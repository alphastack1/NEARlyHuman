NH-010

Confirmed failure and uncertain save

Reviewed visual guide

Build use

Give confirmed Failed a fresh-request path only after the chain records the failure and releases the lock. Keep the prior save, selected supplies and historical transaction inspectable.

State boundary

Unknown is not Failed. Checking an existing final save must not offer a paid retry, reroll, refund, deletion, or prematurely enabled Start day. Read and reconcile the same request and transaction.

Guide notes

Confirmed Failed/released permits a fresh request; uncertain save rechecks the existing one. Back must preserve the same canonical eligibility gate.

NH-011

Expiry available and release pending

Reviewed visual guide

Build use

Expiry becomes callable strictly after the canonical stored deadline. Release expired request is an exceptional owner transaction with network gas only, and must remain reachable when the job backend is unavailable.

State boundary

Passing a clock does not release the pending lock. After broadcast, track the same release hash and canonical request; disable duplicate release and fresh day submission until a terminal transition is confirmed.

Guide notes

Expiry available and release pending both remain locked. Only the first opens gas-only recovery approval; rechecking the submitted release is read-only.

NH-012

Confirmed release and unavailable replay

Reviewed visual guide

Build use

A confirmed release returns to the preserved save and a fresh quote/request when eligible. A missing latest packet uses the compact onchain outcome to reach care, memorial or trial completion.

State boundary

Release does not refund the old attempt or automatically charge for a new one. Missing presentation bytes do not erase the NFT/save or justify another AI call, signature, payment or reroll.

Guide notes

Release preserves LV03/NEXT04; missing latest day-three replay remains LV03/SAVED03 with a saved-outcome exit. Technical packet wording can be simplified in the build.

NH-013

Ownership loss and account reconciliation

Reviewed visual guide

Build use

Remove future care actions immediately when ownership is lost. Account/network changes gate stale actions before rechecking the selected token and supported chain. Keep accepted jobs attached to their original token.

State boundary

A draft belongs to its account/token/network and must never be copied into another rooster. Loaded public replay data need not be erased, but it cannot authorize new actions for an old owner.

Guide notes

Lost ownership is read-only old public state; changed account is neutral checking state. No stale care actions carry into a different account.

NH-014

Living summary and retained memorial

Reviewed visual guide

Build use

Summary shows the current saved needs, survived-day level and consequential events, with every actionable warning preserved. Memorial keeps identity, final cause/day and life summary available.

State boundary

A fatal biological day increments committed days but not survived-day level. Death retains the NFT and ends play; there is no burn, resurrection, salvage, inheritance or later living recovery.

Guide notes

Correct saved LV04 versus terminal LV05/day6, retained NFT and empty bed. The Nutrition change row uses a heart rather than fork; use the written label/correct icon in implementation.

NH-015

Living trial completion and fatal third day

Reviewed visual guide

Build use

Living testnet trial completion means the three committed-day allowance ended while the rooster is alive. A fatal third committed result presents the memorial/dead state first, with trial exhaustion as secondary access information.

State boundary

Failures do not consume committed trial days, although operating spend remains separate. No fourth-day testnet Prepare, fabricated death, guaranteed mainnet availability, or token-migration promise is allowed.

Guide notes

Living trial LV03/day3 is distinct from dead LV02/day3. The alive sentence is sufficient even without a separate ALIVE badge. No fourth trial day or migration implied.

NH-016

Critical next-game-day care and unchanged return

Reviewed visual guide

Build use

Place every urgent condition and its exact due game day before decorative highlights. Suggest useful supply classes without promising Jev will choose them. A long absence preserves biological state, plot progress and output lifetimes.

State boundary

Game-day deadlines are not wall-clock neglect timers. Returning later does not apply new damage, resource loss, fees, disease progression, growth, output aging or a new committed day.

Guide notes

Both panels keep LV04/SAVED04/NEXT05, Serious wound and Infection due game day5 bedtime. Absence changes none of the saved state or deadlines.

NH-017

Empty mailbox and three-unit collection

Reviewed visual guide

Build use

The deterministic mailbox prelude reflects the authorized zero-to-three additions. Empty delivery means use stored supplies; it never creates a fake parcel or starter gift. Collection leads toward the household stores.

State boundary

The right fixture has one water, one bread and one white bandage. These are three distinct whole units, credited once in provisional day state, not three boxes or live player commands. Replay does not credit them again.

Guide notes

Zero delivery has an empty mailbox; the other example collects three distinct authorized inputs. No fake gift, repeated credit or live command.

NH-018

Watering a plot and a later rose harvest

Reviewed visual guide

Build use

Keep exactly two reachable plots with distinct targets and open approaches. Watering consumes one water and sets one plot moisture to two without immediately growing or harvesting it. A later mature rose harvest consumes the planting for its immediate reward.

State boundary

The day-four snapshot is level three; the later day-five snapshot is level four. The apple plot remains a separate growing plant. Harvest creates no stored fruit/rose catalogue type, third plot, tall tree or farm expansion.

Guide notes

Exactly two plots; watering and a later harvest are different recorded days. Moisture/growth values and crop progression follow the written rules.

NH-019

Soap body wash and crafted-chair leisure

Reviewed visual guide

Build use

Body wash consumes one soap and clears the named body contamination. The dry tap does not produce a water unit. Chair leisure uses the one optional chair while the always-available base leisure object remains present.

State boundary

Soap does not cure established disease. The chair does not create currency, permanent equipment or live player furniture commands; it improves the bounded leisure variant and retains its finite life. Keep walking routes and active contact space clear.

Guide notes

Soap body-cleaning is different from established disease treatment. Crafted-chair leisure shares the existing leisure allowance; no furniture editor or player control.
