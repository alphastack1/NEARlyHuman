# Native wallet and world-switch integration

This records the client/UI work and its controlled evidence. A native wallet connection by itself is not a deployed game; final native contract, backend, real Meteor and hosted-release evidence are recorded separately by the PM.

## Shared game, separate authority

The UI now consumes a genuine EVM/native world union. Robinhood retains its numeric chain ID, EVM addresses, original API and transaction transport. NEAR uses `networkId=near-testnet`, named contract/account IDs and native base58 transaction hashes. No fake EVM chain ID, owner address or transaction hash represents NEAR.

Each API object is bound to a particular world. Network selection clears the previous world's NFT number from the URL. Names/strengths, parcel selection, current page, scroll positions, last life and checked wallet can be retained separately for each world. An existing wallet is reused only after a read-only connection probe and matching runtime configuration; a change never transfers an NFT, bridges NHC or silently buys a life. An unresolved financial intent blocks changing worlds.

Exact or remembered NEAR links retain their world when discovery temporarily omits an unreachable service. They show a retry and an explicit network choice, without opening an unrelated Robinhood token number. Malformed mixed-world links stop before reading another world's configuration. Directory discovery shows **Opening networks…** while pending; the current Robinhood hatch remains usable independently. A failed discovery offers only the known current world and an explicit retry.

The native wallet chooser presents Meteor first and keeps other compatible wallets behind a secondary action. Native units and the spendable balance use 24 decimals. Native NHC birth burns directly, with no invented ERC-20 allowance. Token births and purse withdrawal disclose the configured storage deposit and that unused NEAR returns. The public NFT badge includes its network.

## Native payment and recovery boundaries

- The real NEAR Connect package is loaded only for the native world. It is fixed to testnet and requests no function-call key at connection. Free ownership verification uses NEP-413, with the exact selected account, nonce and site recipient.
- Meteor can return multiple connected accounts. The actual sign-in event supplies the selected account; the client does not assume the first result of `getAccounts` is that selection. `expected_owner` is included in custom economic calls.
- Critical native reads verify the testnet RPC, deployed code hash, contract identity and rules, decision policy, relayer and quote signer. Pinned views must return the requested block hash.
- The day quote's Ed25519 signature is verified locally before opening a paid wallet confirmation. Fees, world, player, policy and expiry are checked too.
- Every native economic operation records its exact operation ID, arguments, gas, deposit and selected owner before the wallet prompt. A separate immutable local record prevents another tab's current pointer from erasing that operation. A browser unable to persist the operation is stopped before payment.
- A lost mint/birth/withdraw callback can recover its exact immutable `get_operation` outcome and payload fingerprint without inventing a transaction hash or sending again. Accepted-day recovery compares the entire frozen admission, including zero-reward shipping normalization.
- A known failed duplicate hash cannot be claimed as the earlier successful payment. If its exact business outcome is already canonical, recovery is hashless and the server verifies that outcome directly. A different already-used day payload is treated as replaced and the actual home is refreshed.
- **Retry original transaction** is explicit, never automatic. It reuses the complete original operation ID, method, arguments, owner, gas and deposit. Check remains secondary. Cancelling this retry cannot erase an earlier uncertain request. Canonical completion, a proven replacement or a missing admission strictly after its signed expiry are the retirement boundaries.
- Expiry uses absence and whole-second timestamp from the same final block. Equality is still valid onchain; a later head cannot be mixed with an earlier absence proof.
- Read-only checking is visually distinct from an actual wallet confirmation. A background refund failure cannot negate a committed native game operation.
- Native payment and free-message preflight now finish before a deliberate **Open Meteor** handoff. No application RPC runs after that fresh click and before invoking the SDK. A fresh unsent handoff can be cancelled without a payment; cancellation during an original retry preserves the earlier uncertain operation. Robinhood keeps its existing direct wallet flow.
- Native connection performs static world checks before wallet access, then validates the actual public contract before adopting the account. This keeps slow public RPC work from consuming the connection gesture. FastNear and the official primary RPC are supplied to the SDK; a changed transport invalidates a cached reader without changing authority, request IDs or signature domains.

## Evidence and critique loop

The [compact evidence](wallet-ui-evidence.json) separates all synthetic inputs from actual public Robinhood reads. No wallet private key, real native signature, broadcast, funded quote, financial-ledger write or AI credit was used in these controlled client checks.

1. The existing Robinhood UI regression run passed sixteen narrow, normal, wide and short views, reset, network return and rejected connection, with zero errors or writes.
2. The native two-world browser run exercised the actual SDK with an injected keyless provider and explicitly synthetic undeployed NEAR RPC/config/life data. The core paths passed: separate drafts; cached wallet restoration; actual chosen account despite a second account in the wallet list; native cancellation; immutable lost-hash recovery; empty first parcel; one intercepted NEP-413 verification and quote only at Start; and an unreachable native exact link preserving its world. The native NHC storage screen was inspected too. A final newly added malformed-no-token case initially waited for its error before pressing the first-visit START overlay, so that harness's whole-run exit was not counted as an all-pass. The guarded source made no fallback Robinhood config/life call; this remaining harness step is identified rather than described as a product transaction failure.
3. The explicit retry browser proof passed **A unknown → Check absent → B exact retry cancelled → C exact retry**, preserving the original ID, payload and uncertainty journal throughout. No fresh mint ID or automatic request occurred.
4. Controlled delayed → failed → retried discovery passed, without blocking Robinhood connection, displaying a fake world or leaving permanent loading.
5. Fifteen focused native client checks passed. They include wrong-network/code rejection, exact receipt/fingerprint matching, refund outcomes, failed duplicate-hash recovery, all admission fields, same-block expiry, wrong-block rejection, local Ed25519 verification, fixed original retry, native token birth without approval, and both paid/free fresh-gesture handoffs. The reusable keyless operator is `node node_modules/tsx/dist/cli.mjs scripts/near/check-wallet.ts`; its disposable report is created under ignored TEMP.
6. The later native gesture browser proof passed: fresh handoff cancellation opens no SDK payment; cancelling an app handoff or SDK retry preserves the earlier unknown operation; all actual injected SDK payment calls observe active user activation. A separate fresh-page reconnect fixture reproduces an earlier mint journal without an active wallet, reconnects through the SDK and returns to the pending Retry/Check controls when the operation is absent. It does not get stranded in wallet choices or submit a new mint.

Independent contract review identified the admission-payload, failed-hash, expiry-race, returned-block and retry-cancellation edges above; the client builder implemented each correction and supplied focused evidence. The PM owns the actual Meteor session, developer keys and final financial/publication gate. Both canonical rooster source hashes remain unchanged.
